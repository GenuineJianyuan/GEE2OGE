## 一、整体思路

GEE → OGE 转换分成两条主路径，**LLM 增强路径为默认主力**：

```
GEE JavaScript 代码
        │
        ▼
┌─────────────────────────────────┐
│  6 步规则引擎（CaseStudyPipeline）│
│  Step1 语义抽象 → Step2 API 识别 │
│  → Step3 API 匹配 → Step4 代码生成│
│  → Step5 可行性补全 → Step6 重构 │
└─────────────────────────────────┘
        │
        ▼ (规则引擎先跑完拿到中间产物)
┌─────────────────────────────────┐
│  LLM 增强层（llm_service.py）    │
│  ① 代码分析  ② 构建映射上下文    │
│  ③ Prompt 生成 OGE 代码          │
│  ④ 后处理自动修正                │
└─────────────────────────────────┘
        │
        ▼
  合并结果（LLM 代码优先覆盖 step6）
        │
        ▼
  保存到 resource/gee_oge.db
        │
        ▼
  返回前端展示
```

**核心设计原则**：**单库入口、双引擎互补**
- **单库入口**：所有映射关系（无论 OGE 映射还是 Python 实现）都统一存放在 SQLite 数据库 `resource/gee_oge.db` 的 `operator_mapping` 表中，通过 `mapping_type` 字段区分。运行时只查这一张表。
- **双引擎互补**：规则引擎负责"结构化、可解释"的分析过程（给前端展示步骤链条）；LLM 引擎负责"高质量、地道"的最终代码生成（覆盖 step6 结果）。

## 二、知识库构建（一次性）

### 2.1 数据来源

| 来源 | 路径 | 内容 |
|------|------|------|
| GEE API 元数据 | `resource/gee.json` | 1451 条 GEE API 详细信息（类名、方法名、参数、描述） |
| OGE API 元数据 | `resource/oge.json` | 478 条 OGE API 详细信息（算子名、输入、输出、示例） |
| 映射表 | `resource/gee_to_oge_matches.xlsx` | Excel 人工整理的 GEE→OGE 映射关系（约 250 条有效映射） |
| Python 实现 | `gee_python_functions.py` + `gee_unmatched_functions.py` | ~92 个用 Python 实现的 GEE API |

### 2.2 入库流程（`db_initializer.py`）

```
build_database(force=True)
  │
  ├── init_database()                 # 执行 resource/db_schema.sql 建表
  │
  ├── import_class_mapping()         # 写入 class_mapping（GEE 类 ↔ OGE 类）
  │     来源: 硬编码字典 GEE_TO_OGE_CLASS
  │
  ├── import_gee_api_info()          # 写入 gee_api_info
  │     读取 resource/gee.json，每条记录保留 api_full_name / class_name / arg_types / description
  │
  ├── import_oge_api_info()          # 写入 oge_api_info
  │     读取 resource/oge.json，每条记录保留 api_name / input_types / output_type / samplecode
  │
  ├── import_operator_mapping_from_xlsx()  # 写入 operator_mapping 的 OGE 映射部分
  │     ├── 读 resource/gee_to_oge_matches.xlsx
  │     ├── 调用 _is_pseudo_oge_name() 过滤"占位符"行
  │     │   （如 "Python List"、"print" 等以 Python/print 开头的不是真正的 OGE 算子）
  │     ├── 调用 _determine_mapping_type() 判定映射类型
  │     │   ├── 1 个 OGE API     → one_to_one
  │     │   ├── 多个 OGE API 组合 → one_to_many（步骤存入 combo_steps JSON）
  │     │   └── 无 OGE API        → missing
  │     └── 插入 operator_mapping
  │
  └── import_native_python_implementations()  # 写入 operator_mapping 的 Python 实现部分
        ├── 从 gee_python_functions.GEE_PYTHON_FUNCTIONS 取映射
        ├── 从 gee_unmatched_functions.UNMATCHED_API_FUNCTIONS 取映射
        ├── 去重：若 GEE API 已有真 OGE 映射，跳过
        ├── 调用 _extract_function_source() 用 AST 提取函数完整源码
        └── 以 mapping_type='native_python' 插入 operator_mapping
            （源码存入 native_python_code 字段）
```

### 2.3 统一查询接口

运行时只有一个查询入口（`db_dao.py`）：

```python
dao = GeeOgeDao()
mapping = dao.get_mapping_by_gee_name('ee.Date')
# 返回统一结构，无论哪种 mapping_type:
# {
#   'gee_api':     {api_full_name, class_name, arg_types, description, ...},
#   'oge_api':     {api_name, input_types, output_type, samplecode, ...} 或 None,
#   'mapping_type': 'one_to_one' | 'one_to_many' | 'many_to_one' | 'native_python' | 'missing',
#   'oge_api_id':  指向 OGE API id（one_to_one/one_to_many/many_to_one 时有值）,
#   'native_python_code': Python 源码（native_python 时有值）,
#   'combo_steps':  [OGE 步骤列表]（one_to_many 时有值）,
#   'confidence':   置信度 0~1,
#   'verification_status': 'manually_approved' | 'pending' | ...
# }
```

5 种 `mapping_type` 的差异化处理：

| mapping_type | oge_api 字段 | native_python_code | combo_steps | 处理方式 |
|--------------|--------------|-------------------|-------------|----------|
| `one_to_one` | ✅ | null | null | 直接映射到单个 OGE 算子 |
| `one_to_many` | ✅（第一个） | null | ✅ JSON | 展开成多个 OGE 算子组合步骤 |
| `many_to_one` | ✅ | null | null | 多个 GEE 方法 → 1 个 OGE 算子（需上下文推断） |
| `native_python` | null | ✅ 完整源码 | null | 在代码生成步骤插入 Python 实现 |
| `missing` | null | null | null | 标记为缺失，生成警告 |

## 三、规则引擎 6 步转换（`case_study_pipeline.py`）

### 3.1 入口

```python
from case_study_pipeline import CaseStudyPipeline

pipeline = CaseStudyPipeline()
result = pipeline.run(gee_code)    # 执行 6 步，返回 PipelineResult
pipeline.close()
```

### 3.2 Step 1 — 语义抽象（纯解析，不查库）

**函数**: `step1_semantic_abstraction(gee_code) -> Step1Result`

**做什么**：
1. 将代码按空行切分成若干"步骤块"（workflow_steps）
2. 提取每个步骤的代码片段（raw_snippets）
3. 提取任务目标描述（task_goal）
4. 提取关键参数（key_params）：数据源名、波段组合、坐标等

**输出结构**：
```python
Step1Result {
    task_goal: str                       # "Task decomposed into N steps: Step1; Step2; ..."
    workflow_steps: List[str]            # ["NDVI 计算", "初始化"]
    key_params: Dict                     # {"data_sources": [...], "band_combos": [...]}
    raw_snippets: List[Dict[str, str]]   # [{step_description, code_snippet}, ...]
}
```

### 3.3 Step 2 — API 需求识别（纯解析，不查库）

**函数**: `step2_api_requirement(step1) -> Step2Result`

**做什么**：
1. 对全部代码做**全局变量类型推断**（`_infer_variable_types`）
   - 识别 `var img = ee.Image(...)` → `img: ee.Image`
   - 识别赋值链 `var ndvi = img.normalizedDifference(...)` → `ndvi: ee.Image`
   - 识别运算链 `var result = img.select(...)` → `result: ee.Image`
2. 对每个步骤的代码片段提取 API 调用（使用全局变量类型）：
   - 正则匹配 `ee.XXX(...)` 构造函数
   - 正则匹配 `ee.XXX.yyy(...)` 直接调用
   - 正则匹配 `Map.xxx(...)` 地图操作
   - 正则匹配 `Export.xxx(...)` 导出操作
   - 根据变量类型推断链式调用：`img.xxx(...)` → `ee.Image.xxx`

**输出结构**：
```python
Step2Result {
    required_apis: List[List[str]]    # 每个步骤的 API 列表：[["ee.Image", "ee.Image.normalizedDifference"], ...]
    all_apis: List[str]              # 去重后的全量：["ee.Image", "ee.Image.normalizedDifference"]
    api_count: int                   # 2
}
```

### 3.4 Step 3 — API 匹配（查库 ⭐ 首次查库）

**函数**: `step3_api_matching(step2) -> Step3Result`

**做什么**：
1. 对 Step2 识别出的每个 GEE API，调用 `dao.get_mapping_by_gee_name(name)` 查询映射
2. 记录每个 API 的匹配状态
3. 调用 `dao.calculate_match_rate(apis)` 计算匹配率

**输出结构**：
```python
Step3Result {
    match_details: List[Dict]  # 每条 {gee_api, status: "matched"|"missing", oge_api?}
    match_rate: float          # 0.0 ~ 1.0
    matched_count: int
    missing_count: int
    missing_apis: List[str]    # 未匹配的 API 列表
}
```

### 3.5 Step 4 — 步骤级代码生成（查库 ⭐ 再次查库）

**函数**: `step4_ocode_codegen(step1, step2, step3) -> Step4Result`

**做什么**：
对 Step1 切分的每个步骤，根据 Step3 的匹配结果生成对应的 OGE 代码：

| mapping_type | 生成代码 |
|---|---|
| `one_to_one` | 单个算子调用：`service.getProcess("Coverage.abs").execute(input)` |
| `one_to_many` | 展开成多个组合步骤，添加 `[COMBO]` 注释前缀 |
| `many_to_one` | 对应单个 OGE 算子，添加上下文说明 |
| `native_python` | 标记为 `[PYTHON IMPL]`，输出 Python 源码片段 |
| `missing` | 标记为 `[MISSING]`，生成空代码 |

对每一步代码片段，组装成完整的 OGE 代码段。

**输出结构**：
```python
Step4Result {
    step_codes: List[Dict]  # 每个步骤：{step_index, step_description, gee_code, oge_code}
    feasibility_flags: List[Dict]  # 每个步骤：{step_index, feasibility}
}
```

### 3.6 Step 5 — 可行性补全（纯逻辑，不查库）

**函数**: `step5_feasibility_completion(step3, step4) -> Step5Result`

**做什么**：
1. 检查 Step3 的 missing_apis，判断每个缺失 API 的类型：
   - **UI/可视化类**（`Map.addLayer`、`Map.setCenter`、`print`、`Export`）→ 标记为"非阻断性缺口"，给出替代建议
   - **核心分析类**（`Image`、`Feature`、`Reducer`、`Filter` 等）→ 标记为"阻断性缺失"
2. 生成修复建议（用 print 替代 display，用注释替代 Map 调用等）

**输出结构**：
```python
Step5Result {
    overall_feasible: bool
    blocking_apis: List[str]        # 阻断性缺失
    non_blocking_gaps: List[str]    # 非阻断性缺口
    rescue_suggestions: List[Dict]  # [{api, suggestion}]
}
```

### 3.7 Step 6 — 工作流重构（纯拼接，不查库）

**函数**: `step6_workflow_reconstruction(step4, step5, step1) -> Step6Result`

**做什么**：
根据 Step5 的可行性判定，选择不同的组装策略：

| 可行性 | 组装方式 |
|---|---|
| `blocking_apis` 非空 → `infeasible` | 组装部分可执行代码 + 生成缺失报告 |
| `non_blocking_gaps` 非空 → `partial_feasible` | 组装完整代码（UI 部分用 print 替代） |
| 无缺失 → `full_feasible` | 组装完整可执行代码 |

组装模板：
```python
import oge
oge.initialize()
service = oge.Service.initialize()

# ----- Step 1: <workflow_step_1> -----
# <step1 的 OGE 代码片段>

# ----- Step 2: <workflow_step_2> -----
# <step2 的 OGE 代码片段>
...
```

**输出结构**：
```python
Step6Result {
    oge_code: str                  # 完整可执行的 OGE Python 代码
    missing_report: str | None     # 阻断性缺失报告
    feasibility: str               # full_feasible / partial_feasible / infeasible
}
```

## 四、LLM 增强转换（主力路径，`llm_service.py`）

LLM 增强在规则引擎跑完后追加 3 个增强步骤，**最终用 LLM 生成的代码覆盖 step6**。

### 4.1 可用性检测

```python
llm = get_llm_service()
llm.is_available()  # 先尝试 HTTP 健康检查 /models，失败回退简单调用
# 返回 True / False
```

### 4.2 代码分析（`llm.analyze_gee_code`）

**做什么**：把 GEE 代码发给 LLM，获取：
- 任务目标（task_goal）
- 调用的 API 列表（api_calls）
- 变量类型推断（variable_types）
- 数据流分析（dataflow）
- 改进建议（suggestions）

### 4.3 映射上下文构建（`_build_mapping_context` in `web/app.py`）

**做什么**：
1. 用正则从 GEE 代码提取所有 `ee.*` / `Map.*` API 调用
2. 逐个查询 `dao.get_mapping_by_gee_name(name)` 获取映射详情
3. 组装结构化文本，包含：
   - GEE API 描述、参数
   - OGE API 名、输入类型、输出类型、示例代码
   - 特殊场景补充（`ee.FeatureCollection` 构建、`ee.Filter.date` 日期过滤等）

**输出示例**（供 Prompt 使用）：
```
## ee.Geometry.Point
- GEE 描述: Constructs a Geometry with a single point.
- GEE 参数: coordinates: List, proj: String
- 映射类型: 一对一 (one_to_one)
- OGE API: Geometry.Point
- OGE 输入类型: List, String
- OGE 示例代码: service.getProcess("Geometry.Point").execute([lng, lat], "EPSG:4326")

## 补充说明：FeatureCollection 构建
- 使用 FeatureCollection.loadFromFeatureList
...
```

### 4.4 LLM 代码生成（`llm.generate_oge_code`）

**输入 Prompt 包含 4 部分**：
1. **角色**：GIS 领域代码迁移专家
2. **GEE→OGE 算子映射表**（上一步构建的结构化文本）
3. **OGE 语法指南**（内嵌的完整语法手册）
4. **严格规则**（DO/DON'T 清单 + 常见错误对照表）
   - ✅ 必须用 `oge.Service.initialize()` 而非 `oge.Service()`
   - ✅ 必须用 `service.getProcess("Geometry.Point").execute(..., "EPSG:4326")`
   - ✅ FeatureCollection 必须用 `"FeatureCollection.loadFromFeatureList"`
   - ✅ 全部使用位置参数，禁用关键字参数
   - ✅ filterDate 必须指定第 4 参数 `"system:time_start"`

**LLM 输出**（JSON）：
```json
{
  "oge_code": "完整的 OGE Python 代码",
  "explanations": ["Step 1: ...", "Step 2: ..."],
  "warnings": ["警告信息"],
  "feasibility": "full_feasible"
}
```

### 4.5 后处理自动修正（`llm._post_process_oge_code`）

LLM 生成的代码存在常见错误，用正则自动修正 5 类：

| 错误类型 | 修正规则 |
|---|---|
| `oge.Service()` 误写 | → `oge.Service.initialize()` |
| `oge.Geometry.Point([lng, lat])` 直接调用 | → `service.getProcess("Geometry.Point").execute([lng, lat], "EPSG:4326")` |
| `getProcess("FeatureCollection")` 算子名错 | → `getProcess("FeatureCollection.loadFromFeatureList")` |
| 关键字参数 `geometry=`, `start=` 等 | → 位置参数（去掉关键字） |
| `filterDate` 缺少第 4 参数 | → 自动补充 `"system:time_start"` |

### 4.6 合并策略

```
final_result = rule_result.to_dict()
if llm_generated.oge_code 存在:
    final_result.step6.oge_code = llm_generated.oge_code  # LLM 代码覆盖
    final_result.llm_oge_code = llm_generated.oge_code     # 额外字段
final_result.llm_analysis = llm.analyze_gee_code(...)     # LLM 分析
final_result.llm_enhancements = [..., 规则引擎 + LLM 的所有补充说明]
```

**合并结果**：LLM 生成的代码替代规则引擎 step6 的拼接代码，但保留 step1~step5 的中间产物（用于前端步骤链条展示）。

## 七、关键设计决策

### 7.1 为什么要用"单库入口"？

- 消除分散维护成本：Python 源码文件只在初始化时用一次（AST 提取入库），运行时只读数据库
- 保证一致性：所有查询统一走 `dao.get_mapping_by_gee_name(name)`，不会出现两套逻辑
- 便于扩展：新增映射只需写入 `operator_mapping` 表，无需改代码

### 7.2 为什么要"双引擎互补"？

- **规则引擎**擅长结构化分析：能清晰展示 6 步链条，每个步骤的输入输出都可追溯，便于调试和理解
- **LLM 引擎**擅长代码生成：生成的代码更地道、更符合 OGE 实际语法、参数格式正确
- **合并策略**：用规则引擎的分析产物 + LLM 生成的最终代码，既保留了过程可解释性，又保证了代码质量

### 7.3 为什么要后处理自动修正？

LLM 容易犯的错（`oge.Service()`、`oge.Geometry.Point`、关键字参数等）都是**固定模式错误**，用正则自动修正比让 LLM 自己注意更可靠，也更快（一次正则替换 vs 多轮对话）。

### 7.4 规则引擎 vs LLM 的分工边界

| 能力 | 规则引擎 | LLM |
|---|---|---|
| API 识别与分类 | ✅ 可靠 | ❌ 不稳定 |
| 映射匹配（查库） | ✅ 精准 | ❌ 可能幻觉 |
| 步骤链条展示 | ✅ 可解释 | ❌ 难分步 |
